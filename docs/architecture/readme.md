# How the system fits together

[System diagram](diagram.md) · [Current rules and dated history](../service_contracts.md)

**Customer interface.** Next.js builds a static React site served by Cloudflare Worker Static Assets. The browser browses cached availability, collects details and consent, then calls the protected Worker API. It does not hold provider secrets or decide whether a payment or booking is valid. GitHub Pages serves a separate demo build, not the live checkout environment.

**Application and coordination.** The Worker checks request origin, session/capability ownership and environment identity. The account Durable Object serializes provider workflows with bounded queues and recovery priority. SimplyBook supplies schedules and creates bookings; the server retains each write claim and result before continuing. Batch checkout validates every session and batch closure before creating one HitPay payment request. The current integration uses HitPay sandbox. The customer visits hosted checkout and returns to the site.

**Two storage roles.** D1 stores minimal identity/access, attempt, booking-effect, payment, webhook/reconciliation evidence and display snapshots. It protects retries and unknown outcomes; SimplyBook remains the booking/invoice authority and HitPay the payment authority. The Durable Object has its own persistent SQLite storage for coordination and encrypted provider tokens. Token restoration survives an instance restart without extending original expiry or replacing current identity/payment checks.

**Recovery and notification.** Webhooks and browser return are triggers, not proof. The minute scheduler drives due reconciliation and availability warming (approximately every 15 minutes for display). Recovery reads authoritative payment state, reconciles SimplyBook and publishes confirmation only after valid booking and paid-invoice evidence. The browser performs bounded status checks and retains terminal confirmation. Turnstile and Resend support identity verification; SimplyBook sends the accepted booking notification on final payment confirmation. Identity emails and booking emails have different owners.

**Observability.** Existing sanitized diagnostics expose queue, checkout, storage, token and recovery measurements. A separate Tail Worker is prepared to export allowlisted summaries as OpenTelemetry OTLP/HTTP to the owner's company central Grafana Cloud account, where the supplied dashboard can query them. Staging and client production require separate ingestion credentials and explicit service/environment labels; the client does not need a separate Grafana account. The Tail Worker is currently disabled/unattached and Grafana is not connected. Export runs outside the customer request path. Correlation attributes join related work; they do not claim continuous parent-child traces across every background operation. Credentials, customer details and checkout URLs are excluded.

**Delivery today.** GitHub verifies frontend, backend and live-email gates before main deployment consumes the tested artifact and applies pending migrations. The optional target workflows now separate staging and closed client release configuration, seal target artifacts and verify revisions before deployment. The legacy main path remains active until a reviewed repository-variable cutover. See the README configuration reference.

**Staging and production target.** One client-owned repository becomes the source of truth. The prepared staging workflow manually deploys a reserved, verified candidate to the developer's existing Cloudflare account; automatic trusted PR deployment remains deferred. After acceptance and merge, main CI verifies the merged revision; an explicit manual production workflow checks current main and its three target verification gates (compatible with GitHub Free private repositories). Production uses separate client-owned Cloudflare resources. Each environment has scoped deployment credentials, bindings, provider mappings and Worker secrets. Staging uses a separate SimplyBook test account and HitPay sandbox; production uses client live accounts. Routine CI uses isolated synthetic providers and does not consume trial bookings. A replacement test account requires validated credentials, mappings and schedules, not new Cloudflare infrastructure.

**Client public entry (prepared).** Cloudflare for SaaS on the client-owned `soccerbotsg.win` zone routes custom hostname traffic to the application Worker with Static Assets and same-origin `/api`. The zone-scoped `*/*` Worker route handles customer hostnames; `run_worker_first: true` makes the application check the canonical origin before serving assets. Workers.dev and previews are disabled for client targets. Deployment preflight verifies zone/account identity, active fallback origin and its proxied originless DNS record, and rejects competing Worker routes. DNS and custom hostname registration remain owner-operated. The first test origin is `https://booking.standardsoftwares.com` with DNS in Primary; the test apex follows as a separately configured and verified target. The eventual origin is `https://soccerbotsg.com`, with Uncoverin retaining DNS. The optional Pages adapter remains supported and tested, but is not selected by the client target.

**Handover and releases.** Preserve the existing staging Worker, D1 data and Durable Object identity; configure client resources and validate first-install/rerun behavior before UAT. Once the client repository controls both targets, disable deployment from the old repository. Deploy the exact artifact verified for each environment: frontend build-time settings such as Turnstile may require separately verified builds from the same revision. Keep migrations backward compatible with ongoing attempts; code rollback does not reverse database or provider effects. These are planned delivery relationships, not configured approval gates or a production-readiness claim; [Service Contracts](../service_contracts.md#deployment-migration-and-acceptance) owns release safeguards.

For a recursive feature-to-file navigation map, see [Code owners and feature map](../code-owners.md).
