# Architecture decisions

| Decision                                          | Rationale                                                                                                                                                          | Revisit when                                                                                                           |
| ------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------- |
| ADR-001 · React/TypeScript and Next static export | The customer site needs interactive selection and protected APIs. Static assets can be served from the same origin without a separate rendering server.            | A real requirement calls for request-time rendering, or measured bundle cost affects the booking path.                 |
| ADR-002 · Worker and Static Assets                | One origin serves the site, validates requests and holds provider credentials. Pages serves the separate preview.                                                  | Runtime limits or hosting requirements change. A static mirror cannot accept bookings.                                 |
| ADR-003 · Account coordinator and D1              | One account coordinator serializes writes affecting shared studio capacity. D1 retains attempt, payment and recovery evidence across browser and Worker lifetimes. | Measured contention justifies partitioning by independent provider account. Preserve one writer per shared resource.   |
| ADR-004 · SimplyBook and hosted HitPay            | SimplyBook owns bookings and invoices. Hosted payment keeps card entry with HitPay. The Worker matches the payment and invoice before confirmation.                | Provider entitlements, payment routing or merchant/account mappings change.                                            |
| ADR-005 · Email proof and server-issued access    | A guest can book without a profile. Email verification grants access to the matching protected identity and optional saved contact.                                | Session or provider identity requirements change. Browser storage cannot grant authority.                              |
| ADR-006 · Sanitized diagnostics                   | Allowlisted telemetry permits cross-provider timing analysis without sending customer payloads to Grafana.                                                         | Sampling, cost or retention requirements change. Verify receiver ingestion and alert delivery separately.              |
| ADR-007 · Verified release artifacts              | Target-specific verification and deployment of its sealed artifact bind code, configuration and source revision together.                                          | Changing target, build or runtime requires a new verification.                                                         |
| ADR-008 · Same-account native custom domain       | The client target serves soccerbotsg.com directly on the existing Worker with managed TLS. The earlier SaaS fallback supported independently managed DNS.          | Additional customer domains, DNS ownership or routing change. Recheck apex, redirects, mail records, TLS and rollback. |

- Register new foundations through the authenticated internal management service. Routine deployments reuse the registered identity.

## Scaling review and fallback readiness

| Pressure or failure         | First evidence to collect                                             | Candidate response                                                                   | Preserve before changing architecture                                      |
| --------------------------- | --------------------------------------------------------------------- | ------------------------------------------------------------------------------------ | -------------------------------------------------------------------------- |
| More page visitors          | Asset/frontend timings and request volume                             | Optimise actual bundles/cache behavior; check platform plan                          | API authorization and environment-specific build settings                  |
| Checkout queue saturation   | Wait/rejection rate, provider latency, cold/warm and single/batch mix | Address measured bottleneck; review provider capacity and bounded admission          | One scarce-resource authority, recovery priority and claimed-effect fences |
| More venues/accounts        | Independence of capacity, provider quotas and identity scopes         | Design explicit tenant/account partitioning                                          | Tenant isolation, global/shared constraints and old in-flight attempts     |
| D1 latency or size pressure | SQL versus call latency, query patterns, volume and retention needs   | Review queries/limits/placement; evaluate data-store migration if justified          | Foundation, compatible migrations and replay-safe journals                 |
| Provider outage             | Authoritative retained state and upstream status                      | Recover/hold affected attempts and operator escalation                               | Original references; no fallback double booking/charge                     |
| Cloudflare outage           | Impact across assets, API and state; provider financial effects       | Approved continuity plan; prepare alternative infrastructure only after state design | Consistent restore points and single active writer                         |
| Telemetry outage            | Producer/exporter/receiver evidence                                   | Restore visibility or use available platform diagnostics                             | Privacy controls; no assumption of historical replay                       |
| CI/service disruption       | Last verified artifact, revision and schema compatibility             | Restore delivery service or approved recovery procedure                              | No rebuilding/merging around verification safeguards                       |

No alternate stack in this document is deployed as hot standby. Before treating one as a backup, define ownership, current pricing/limits, RPO/RTO, data/export format, restore method, secrets/DNS transition, old/new writer fencing, in-flight payment reconciliation and a rehearsed acceptance/rollback plan. A source ZIP, static mirror or provider export alone is not a complete recoverable system.
